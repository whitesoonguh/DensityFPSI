# Fuzzy Private Set Intersection under Density-Bounded Assumptions

## Overview

Existing fuzzy PSI (FPSI) protocols rely on **separation-based** assumptions —
*"items are at least 2δ apart"* (which costs `O(2^d)` and only works for tiny
`d`) or *disjoint projection* (which is only justified for high-dimensional
data). No single separation-based protocol handles both regimes.

This work replaces separation with a **density-bounded** assumption, the
**C-max collision property**: items may collide inside a δ-ball, but the
multiplicity of collisions *per axis* is bounded by `C`. Under this assumption
we build the first FPSI protocol for the ℓ∞ metric that:

- handles **low- and high-dimensional regimes simultaneously**,
- scales **linearly** in both set sizes and the dimension `d` (for fixed `C`),
- uses **only symmetric-key primitives** (no public-key crypto).

The construction reduces fuzzy matching to an **oblivious selected set
intersection (OSSI)** over per-axis membership tags, instantiated from a
shared-output OPPRF (so-OPPRF) and a secret-shared set intersection (S³I).

## Scope of this artifact

This is a **single-process benchmark prototype** measuring local compute time
plus a formula-based online communication transcript. There is no live network:
the one-time interactive PCG/OT seed exchange, socket scheduling, serialization,
and RTT latency are not modeled.

Both classes of correlated randomness can be produced by **really running their
generators**, single-process:

- the **S³I OLE** correlations are always produced by the Ring-LPN PCG backend
  (`pcg/`) — really executed and timed, with tape refills on exhaustion;
- the **so-OPPRF OT** correlations (the AltMod-WPRF F4 mod-2 OT layer) have two
  selectable backends:
  - **default** (`-DSOOPRF_WITH_LIBOTE=OFF`): a PRG-generated **ideal local
    tape**, standing in for real base OTs;
  - **real** (`-DSOOPRF_WITH_LIBOTE=ON`): correlations generated by **actually
    running libOTe silent OT** (`MultType::Tungsten`) in a single process, so
    the offline OT-correlation generation is real and timed — mirroring the OLE
    side. This realizes the §7.2 instantiation of the so-OPPRF OTs
    (the `~256·dCN` 1-out-of-2 OTs of §E.2).

In **both** OT backends the *online* OT transcript (the mod2OtF4 derandomization
round) is still formula-accounted, not socket-measured — exactly as for the
single-process PCG/OLE. The real backend makes correlation *generation* real; it
does not add a live network.

What is **implemented and measured**:

- C-max collision verification (Algorithm 1) and the `cmax` of generated sets,
- membership encoding,
- so-OPPRF over RB-OKVS with the AltMod weak-PRF,
- PCG-backed secret-shared (r)OLE for S³I — really executed and timed,
- the AltMod-WPRF F4 mod-2 OT correlations — PRG ideal tape by default, or
  **really generated and timed via libOTe silent OT** with
  `-DSOOPRF_WITH_LIBOTE=ON`,
- the S³I subproduct-tree / random-linear-combination / gcd nonempty test.

What is **abstracted or not yet included** (see *Limitations*):

- the **live-network** layer: PCG and silent OT run single-process, so the
  one-time interactive seed exchange, socket scheduling, serialization, RTT, and
  the online OT derandomization round are not socket-measured,
- the final `F_OT` retrieval of matched sender items (the benchmark stops at
  match bits).

Numbers from this artifact are meaningful for the **algorithmic offline
correlation-generation, online compute, and online-transcript** claims; they are
not end-to-end networked protocol timings.

## Requirements

- **Toolchain:** CMake ≥ 3.20, Ninja, and a C11 / C++20 compiler (GCC or Clang).
- **CPU:** x86-64. Pick the build profile that matches your CPU (see *Build*):
  - **`release`** — the paper's reference profile. Requires `AVX512F/BW/VL/DQ`,
    `VAES`, `VPCLMULQDQ`, `AES-NI`, `PCLMUL` (Intel Ice Lake / Sapphire Rapids,
    AMD Zen4). All reported numbers use this profile.
  - **`release-no-avx512`** — for CPUs **without** AVX-512 that still have
    `VAES` + `VPCLMULQDQ` + `AVX2` (e.g. AMD Zen3 / EPYC Milan). Builds and runs
    correctly; numbers are **not directly comparable** to the AVX-512 reference.
- **Real OT backend only** (`-DSOOPRF_WITH_LIBOTE=ON`): additionally `python3`,
  `nasm`, `libtool`, `autoconf`, `automake`, `pkg-config`, `libssl-dev`,
  `libgmp-dev`, `wget` to build libOTe and its dependencies (cryptoTools,
  coproto, sodium, boost). `autoconf`/`automake` are required by libsodium's
  `autogen.sh`.

> **SIGILL pitfall.** The configure-time SIMD check only verifies that the
> *compiler* accepts the flags, **not** that the *CPU* can execute them. Building
> `release` on (or for) a CPU that lacks AVX-512 will compile fine but crash at
> runtime with `Illegal instruction (core dumped)`. On such CPUs use
> `release-no-avx512`.

## Build

A build is two orthogonal choices: a **CPU profile** (preset) and, optionally,
the **real OT backend**.

### 1. Pick a CPU profile

```bash
# AVX-512 reference profile (paper numbers); binaries land in build/
cmake --preset release
cmake --build --preset release -j
ctest --preset release --output-on-failure

# No-AVX-512 profile (VAES/VPCLMUL/AVX2 via -march=native); binaries in build-no-avx512/
cmake --preset release-no-avx512
cmake --build --preset release-no-avx512 -j
ctest --preset release-no-avx512 --output-on-failure
```

Manual invocation (e.g. to set the output dir yourself):

```bash
cmake -S . -B build -GNinja -DCMAKE_BUILD_TYPE=Release \
  -DFPSI_ENABLE_AVX512=OFF -DFPSI_REQUIRE_AVX512_VAES_VPCLMUL=OFF   # drop both -D for AVX-512
cmake --build build -j
```

### 2. (Optional) real OT backend (libOTe silent OT)

libOTe is fetched and built as a local third-party dependency under
`thirdparty/out/install`, then consumed via `find_package(libOTe)`. The build
script pins the same libOTe commit that secure-join (the AltMod-WPRF reference)
builds against, so `MultType::Tungsten` + silent OT/VOLE are guaranteed present.

```bash
# one-time: fetch + build libOTe into thirdparty/out/install
bash thirdparty/build_deps.sh

# add -DSOOPRF_WITH_LIBOTE=ON to either profile, e.g.:
cmake --preset release -DSOOPRF_WITH_LIBOTE=ON           # AVX-512 reference
# or
cmake --preset release-no-avx512 -DSOOPRF_WITH_LIBOTE=ON # no AVX-512
cmake --build --preset release -j                        # (match the preset you configured)
```

With the flag set, `bench_fpsi`'s offline OT-tape timer reflects the real
libOTe silent-OT run, and `--verbose` reports the generated correlation counts
(`ot_tape_silent_gen_seconds`, `ot_tape_f4_correlations`,
`ot_tape_key_correlations`, `ot_tape_silent_ot_instances`). Without the flag
these fall back to the PRG tape (`ot_tape_silent_gen_seconds = 0`).

### Docker (reproducible real-OT build)

The image builds the real-OT configuration end to end. AVX-512 is **off by
default** so the image runs on any AVX2 + VAES + VPCLMUL host; enable it with a
build arg when both the build and run CPUs support AVX-512.

```bash
docker build -t densityfpsi .                              # no-AVX-512 (default)
docker build --build-arg ENABLE_AVX512=ON -t densityfpsi . # AVX-512 reference profile

docker run --rm densityfpsi          # default bench_fpsi invocation
docker run --rm densityfpsi ./build/fpsi/bench_fpsi 30 65536 65536 16 4 1 --verbose
```

## Benchmark reference

### FPSI (main)

```bash
./build/fpsi/bench_fpsi [delta M N d C iters] [--verbose|-v]
```

| Arg | Meaning |
| --- | --- |
| `delta` | ℓ∞ matching radius δ |
| `M` | receiver set size |
| `N` | sender set size |
| `d` | item dimension |
| `C` | max membership-tag size for S³I (**must be a power of two**) |
| `iters` | repetitions |

Default output:

```text

params: delta=30 M=65536 N=65536 d=16 C=4 iters=1
correctness: forced_hits=4096 observed_hits=4096 cmax=4
offline_seconds=...
online_seconds=...
total_seconds=...
comm_r_to_s_MB=...   comm_s_to_r_MB=...   comm_total_MB=...
```

(The header string `ideal OT/OLE tape` is unchanged for log compatibility; the
OLE correlations are real PCG compute, and the OT correlations are real libOTe
silent OT when built with `-DSOOPRF_WITH_LIBOTE=ON`.)

`--verbose` adds per-phase offline/online timings, per-`Y`-item latency, the
directional communication accounting, operation counts, and — for the OT tape —
the silent-OT generation time and correlation counts.

Quick sanity sweep after building:

```bash
ctest --preset release --output-on-failure
./build/gf64/bench_gf64_core 262144 4096 16
./build/pcg/bench_pcg 20 4 3 3 8
./build/okvs/bench_okvs_core 65536 65536 218 0.10
./build/opprf/bench_opprf 4096 4096 3
./build/fpsi/bench_fpsi 30 4096 4096 16 4 1
```

the run should be discarded).

## Online vs. offline convention

- **offline** = input-independent local preprocessing: membership encoding,
  sender key generation, OSSI slot expansion, OPPRF PRF masking, RB-OKVS
  encoding, AltMod-WPRF OT-tape generation (PRG, or real libOTe silent OT), and
  PCG/OLE correlation generation.
- **online** = tape consumption and downstream compute: AltMod-WPRF tape
  materialization, receiver OKVS decode, and the S³I arithmetic + gcd nonempty
  test. PCG/OLE correlations are fully materialized *before* the S³I online
  timer starts, and `s3i_online_seconds` is measured directly (not derived by
  subtracting PCG time from an enclosing timer).

Party convention: `R` = FPSI receiver = OPPRF sender = S³I output receiver;
`S` = FPSI sender = OPPRF query holder = S³I sender.

`bench_fpsi` reports only the **directional online transcript** bytes, not the
expanded local preprocessing tapes. The accounting in `--verbose` follows:

```text
okvs_hint_r_to_s_bytes        = okvs_cols * 8
sooprf_key_mult_s_to_r_bytes  = key_mult_blocks * 2 * 16
sooprf_f4_choice_s_to_r_bytes = f4_blocks * 2 * 16
sooprf_f4_msg_r_to_s_bytes    = f4_blocks * 2 * 16
s3i_ole_correction_*_bytes    = scalar_ole_correlations * 8   (each direction)
s3i_hs_reveal_s_to_r_bytes    = N * 2 * (2*C) * 8
```

## Limitations

- `C` must be a power of two (the S³I subset tree follows the paper's
  power-of-two presentation).
- The field is `GF(2^64)`; failure probabilities that depend on `|F|` are at
  64-bit scale unless amplified.
- The benchmark uses the **weak** `F'_OSSI` nonempty predicate by default, not
  full intersection element recovery.
- Final item-retrieval OT is not included, but we account for the required communication cost for this in the paper.
- The so-OPPRF OT correlations (AltMod-WPRF F4 mod-2 OT) are a PRG ideal local
  tape by default. Building with `-DSOOPRF_WITH_LIBOTE=ON` generates them with
  real libOTe silent OT, so offline OT-correlation generation is real and timed;
  the *online* OT transcript (the derandomization round) is still
  formula-accounted, and PCG/OLE likewise runs single-process — live seed
  exchange, socket scheduling, serialization, and RTT are out of scope. In this paper, we account for the communication latency through estimation; i.e., dividing the total communication cost by the network bandwith and addressing the RTT latency via counting communication rounds.
- The `release-no-avx512` profile bundles the gf64 batch VPCLMUL kernel behind
  the AVX-512 toggle, so on no-AVX-512 CPUs gf64 falls back to a scalar path.
  Such builds run correctly but their timings are not comparable to the
  `release` (AVX-512) reference profile.
